# core/notifications

**Owns:** schema `notifications.*` — notifications (inbox + push queue: category, status pending/sending/sent/delivered/failed/suppressed, scheduled_for, read_at), device_tokens (platform, native_token, active), campaigns (one per broadcast offer: status pending/running/done, `last_member_id` cursor, UNIQUE source_event_id, `not_before` — the offer's publish time, 0036).
**Publishes:** `notification.delivered`, `notification.failed` (noConsumer; analytics).
**Consumes:** `offer.published` → personal: one row for the target (consent + quiet hours + the daily cap, UNIQUE member+offer+category), scheduled from the later of now and the offer's `publishedAt` — never pushed while it is still invisible; broadcast: one `campaigns` row (UNIQUE source_event_id) with `not_before = publishedAt`, nothing else in the delivery · `offer.withdrawn` / `offer.expired` → close the offer's open campaign, then suppress pending · `request.status_changed` → transactional "Your quote is ready" when `to=quoted`; `to=closed|booked` suppresses that request's pending transactional row (`last_error = request_moved_on`; a row already `sending` finishes) — dispatch cannot ask requests (domain), so the event carries the state · `member.deleted` → delete tokens + rows.
**Daily cap:** at most one offer push (personal or broadcast) per member per day — the day it is sent, in the member's zone, after quiet hours and not before its offer is published (`daily-cap.ts`). A member is capped when another offer push of theirs, whatever its status, is scheduled on that same local day, whenever it was created: one query per page (or per personal offer) by `scheduled_for` over the window around the send (`notif_offer_sends`, 0044), the day compared with the Intl data quiet hours use. It once counted the rows created since the server's UTC midnight, while quiet hours move a push to the next morning.
**Time zones:** a member's stored zone that is not one (`safeTimeZone`) counts as `America/New_York`, the members default, with a warn `{ memberId, reason: "invalid_time_zone" }` — it never fails a campaign page or a delivery. Quiet hours (22:00–08:00) and the daily cap's day read the member's clock from Postgres's tzdata (`afterQuietHours`, `localDays`: one statement per page, #114); a zone name Postgres does not read counts as the default too (`zonesForPostgres`, Postgres's names listed once per process).
**Devices:** `POST /v1/devices` upserts by (member, device); a native token belongs to the phone's current member (UNIQUE native_token), so the row another member — or this member's earlier install — holds for it is removed in the same transaction (a racing registration is retried once).
**Inbox:** `GET /v1/inbox` and `unreadCount` list the member's rows that are not suppressed and, while pending, are due (`scheduled_for <= now()`); a failed push stays listed — the inbox is the in-app record. `POST /v1/inbox/:id/read` with an id that is not a UUID is 404.
**Ports:** `PushSender.send(platform, token, payload)` (integration/push), `Members.timezoneOf/getStatus/preferencesOf/audiencePage/deliverabilityOf`. A claim (inline or a stream batch) reads its members' status and preferences in one call (`deliverabilityOf`) and their active devices in one read (ADR-IMPL-077), each list bound as one array (`anyText`), so a statement's text does not change with the claim's size.
**Facade:** `inbox(actor)`, `unreadCount(actor)`, `markRead(actor, id)`.
**Jobs:** `retention-notifications` (daily, ADR-IMPL-077: rows sent, delivered, failed or suppressed after 90 days, done campaigns after 180, in batches, each table a step of its own (`retainEach`); never a pending or sending one; the notifications by `notifications_retention`, `created_at` where the status is one of the four, 0054), `campaign-fanout` (every minute, singleton: claims the oldest open campaign that is due — `not_before` null or past — and pages the audience 1 000 members per transaction — one cap query per page, quiet hours per time zone, ON CONFLICT DO NOTHING, cursor in `last_member_id`), `dispatch` (poller-style loop: advisory lock via job singleton, SKIP LOCKED 100, ≤20/s, recheck status+prefs at send), `receipts` (sent without delivered > 24 h → receipt_unknown), `cleanup-devices` (inactive 180 d).
**Out of scope:** email/SMS channels, in-app chat, segment fan-out (campaigns; no cross-schema JOIN to offer_targets).
**Invariants tested:** dedupe by unique index · broadcast delivery writes one campaign and zero notifications · a campaign resumes after a crash without duplicates · withdrawn offer → suppressed · a withdrawn/expired offer's campaign stops, before or during fan-out · dead token deactivated on Unregistered/BadDeviceToken · quiet hours with member timezone · the daily cap counts the day of sending in the member's zone: around UTC midnight, across quiet hours, and for an offer published for later (`campaign-fanout.test.ts`, `on-offer-published.test.ts`) · transactional bypasses consent and quiet hours · mark-read is scoped (foreign row → 0) · payload contains no PII · a quote push waiting to go is suppressed when its request is closed or booked · the inbox never lists a suppressed or not-yet-due row · a second member registers a phone's token (never 500) and the first member's pushes stop reaching it · an invalid stored time zone never fails a campaign or a delivery · an offer published later is pushed then (personal row and campaign).
