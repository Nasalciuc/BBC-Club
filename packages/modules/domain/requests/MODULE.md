# domain/requests

**Owns:** schema `requests.*` — `requests` (member fare/offer requests), `request_events` (status timeline).
**Publishes:** `request.submitted` (same tx as insert), `request.status_changed` (CRM webhook, operator links). A webhook's `note` is shown to the member under the current step of the request's timeline — written for the member, never for colleagues. A status only moves forward: received → assigned|quoted|booked|closed; assigned → quoted|booked|closed; quoted → booked|closed; booked → closed; closed → nothing (`not_sent` is never set here). The row is read `FOR UPDATE`, so racing webhooks or a double click write the step and publish it once (the others read `unchanged`); a step back is refused and writes nothing — the webhook answers 409 CONFLICT with `context { from, to }`, the operator page `Already booked — nothing changed.` / `This request is closed — nothing changed.` (200).
**Consumes:** `request.submitted` → `requests.onRequestSubmitted` (records that the row is ready to send; no network). The partner call lives in `send-requests`. `member.deleted` → redact contact fields, null `member_id`, close the row (operator may still have a CRM lead).
**Submit:** `Idempotency-Key` is 8–200 letters, digits, `-` or `_` (else 400). The body is `SubmittedRequestBody` (packages/shared): a trip that can be flown — round = there and back, one way = one leg, multi-city 2–6, no leg ends where it starts, dates non-decreasing, no more infants than adults, no NUL — on no day before UTC yesterday (`earliestLegDay`). A replay already committed is answered at once, before the day is checked (a phone that never got its answer may retry after the trip's day); otherwise one transaction takes an advisory lock on the key, looks the key up again, counts the address's (`requests.submit.ip`) and the member's (`requests.submit`) quota on its own connection, reads the catalog and proposals, and inserts — so concurrent replays spend one unit, and a refusal (a 429, a fare or offer that does not match) rolls back and spends none. A 429 carries `context { scope: "ip" | "member" }`. A fare request's fare must exist and be its trip (outbound route and cabin; a fare closed since is taken); an offer request's offer must be one the member could see (withdrawn or expired ones are taken). `GET /v1/requests/:id` with an id that is not a UUID is 404.
**Ports:** `crm.submitRequest(payload) → { crmRequestId }`; `proposals.getVisible` / `getAny` — the offer a request names (submit) and the offer the specialist's e-mail names (send time), one read by key each, never fatal (an error or a timeout over 1 s checks nothing and counts `bbc_request_offer_unavailable{reason}`); `catalog.indicativeFor(route, cabin)` — the estimate a quote's search showed, asked only when the app says it showed one (`estimateShown`), before the insert, never fatal (an error, a timeout over 1 s or an invalid amount counts `bbc_request_estimates_unavailable{reason}`; ADR-IMPL-042); with `catalog.site_prices` on the catalog answers the site's stored price or the formula, never calling the site (ADR-IMPL-063), and the request records who priced it — `shown_estimate_source` (`site` | `club`, CHECK `requests_shown_estimate_source`, 0040; null while the flag is off: the formula), `shownEstimate.source` on `request.submitted`, `shown_estimate.source` to the CRM; `catalog.getAirports(codes)` — the destination's city, one batched read per answer, never fatal (`bbc_request_cities_unavailable`, log `request cities unavailable`); `catalog.getFare(id)` — a fare request's fare, one read before the insert, for what the request keeps of it as it stood when the member asked: its published price and that price's source, kept only when the fare still costs what the app sent (ADR-IMPL-046), and its airline — the name, else the code (the name its page shows), with the code when it is two letters or digits — kept whatever the fare costs now (ADR-IMPL-056); never fatal (an error or a timeout over 1 s records neither and counts `bbc_request_published_unavailable{reason}`).
**Facade:** `listForMember` (requests in progress first, newest first), `get`.
**View (`toRequestVM`, internal):** `route` is the outbound leg and `dates` the frames' `Oct 12–19` (`@bbc/shared/requests/display`, shared with the app); `city`, `tripType` and `phone` (the number the specialist calls) for the titles and the detail; `publishedAtRequest`, the struck fare beside a ready quote's fare (Figma 233:4204); `carrier`, the airline the request was made for (`{ code, name }`, the code null when the fare had none; 3.0 images 08 and 11, ADR-IMPL-056). The member's state: what the CRM or an operator set; otherwise `received` while the request waits for `send-requests`, `not_sent` after six failed attempts or 45 minutes.
**Jobs:** `send-requests` — each minute; a failure is tried again five minutes later (`SEND_RETRY_MINUTES`), six times (`MAX_SEND_ATTEMPTS`; its claim reads `requests_unsent`); giving up logs an error, counts `bbc_request_sends_given_up` and posts to `OPS_WEBHOOK` (RUNBOOK, "A request that was never sent"). A row it cannot read counts as a failed attempt; a closed row is never sent. The payload (`CrmRequestPayload`) names the fare or offer — `fare_id`, `offer_id`, `price_at_request`, `published_at_request`, `carrier`, and the offer as it reads at send time — and `_attempt` (a resend may duplicate a mail a timed-out send delivered). A failed send's stored and logged error is `errorLine(err)` (@bbc/db): never a failed query's parameters.
**Operator links:** `/ops/requests/:token` answers HTML only; past `ops.link` (30/min, burst 10, per address — it protects the tokens) it is an HTML 429 with `Retry-After`: `Too many links at once — wait a minute and open it again.`
**Out of scope:** catalog/fares, campaigns, respond-to-offer (deleted — one request path only).
**Invariants tested:** Idempotency-Key → one row · another member reusing the key → 409 · IDOR → 404 · ownership in WHERE · send-requests stops after six · CRM mock records payload. Estimate (ADR-IMPL-042): only on a quote whose app showed one, recomputed by the server (a price in the body is dropped), the search's own number with its rules' fingerprint — or, with the site's prices on, the site's number the search stored, recorded as `site` with no fingerprint, the formula's as `club`, and the site never asked from the submit (ADR-IMPL-063) — none beside published fares or outside North America, none on a replay or a rate-limited request; an error, a timeout or a bad amount never refuses a request · the published price (ADR-IMPL-046): read from the fare, both or neither with its source, none for a fare re-priced since the app showed it, and a failed read never refuses a request · the airline (ADR-IMPL-056): read in the same fare read, never from the body, a code always with its name (CHECK, 0030), kept for a re-priced fare, none for a quote or an offer, and the request keeps it when the fare changes · the member's note reaches the specialist, quoted · route = the outbound leg, never origin → origin · a city that cannot be read is no city · a new request reads `received`, `not_sent` once the job gives up · the note is redacted on `member.deleted` and a closed row is not sent · an operator link never verifies while `OPS_LINK_SECRET` is empty (ADR-IMPL-047) · statuses forward only, once under a race, a stale link or a deleted member's request never reopened · five concurrent replays cost one unit · a committed replay is answered after its day has passed · 429 says its scope · an Idempotency-Key past 200 characters is 400 · a trip that cannot be flown, an unknown fare or offer, or a fare request for another trip is 400 with its field · the operator e-mail names the fare/offer and marks a resend · a failed send stores no query parameters · a non-UUID id is 404 · the operator 429 is HTML.
