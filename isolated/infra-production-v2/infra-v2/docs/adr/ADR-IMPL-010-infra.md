# ADR-IMPL-010 — Infrastructure: one machine, layered compose, backup from day one
Status: accepted · Date: 2026-09-11 · Supersedes nothing; implements ADR-IMPL-002.

**Decision.** One EU VPS with Docker Compose. A single `docker-compose.yml` plus overlays for staging/production/test — one source of truth, three modes. Only Caddy (80/443) and SSH (22) listen on the internet; Postgres, MinIO, GlitchTip and Uptime Kuma are reachable only through an SSH tunnel. Backups exist from the first day: pgBackRest full daily + continuous WAL to object storage **outside the machine**, encrypted, with an automatic monthly restore drill that asserts the restored shape. Deploy is seven idempotent steps with a pre-deploy dump, expand-only migrations as a separate job, and **automatic rollback** when `/ready` stays red for 60 s. Secrets live in a root-owned 600 env file, rotated with a double window (`_NEXT` accepted alongside the current value), with a copy in the company password manager. Alerts split into `#bbc-ops` and `#bbc-sec`, with phone escalation only for "API down > 5 min". Staging runs on the same machine — with its own Postgres container and volume — until the first real offer reaches a client. `eas.json` lives here, because build profiles are environment configuration.

**Rejected.** Kubernetes and Terraform (one server, one operator). A secret manager (moves the bootstrap-secret problem, adds a service). Sharing a database between staging and production. Publishing Postgres on the host. `:latest` in production.

**Consequences.** A new VPS becomes staging in ~15 minutes with `bootstrap.sh`. A failed deploy restores itself. A backup nobody restored is caught within a month, automatically. Anyone with SSH and the password manager can operate the system — which is the point of the runbook.

**Amendment (code review, same day).** pgBackRest must run inside the Postgres container (archive_command executes there) with options as `PGBACKREST_*` env vars — the config file does not interpolate. One Caddy holds both domains; staging is extra services in the same compose project (a second Caddy on 8443 could never obtain a certificate). Caddy does not depend on the API. Networks: `edge` (caddy, api) and internal `data`. Host cron owns backups, the restore drill and the disk alert; the container cron only fires HTTP jobs. `restore-test.sh` uses the production image (uid parity). `deploy.sh` guards the first deploy (no rollback target). Cloudflare `trusted_proxies` so per-IP logic sees the client. `apps/api/Dockerfile` and `api-deploy.yml` are part of this ADR.
